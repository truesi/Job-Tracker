# Основы system design

## Как вести интервью
- **Уточни** функциональные требования (что делает система) и нефункциональные (масштаб, задержка, доступность, согласованность, надёжность хранения, стоимость). Договорись, что вне рамок.
- **Оцени**: пользователи → запросы в секунду (средние и пиковые), объём хранения в год, трафик. Округляй смело.
- **API** и **модель данных**, затем **высокоуровневый дизайн** (клиенты, балансировщик, сервисы, хранилище, кэши, очереди).
- **Углубись** в самые сложные части и узкие места; обсуди **компромиссы** и **сценарии отказов** (что если этот компонент умрёт?).
- Веди разговор и думай вслух. Единственно правильного ответа нет, есть только обоснованные решения.
- Полезные числа: 1 день ≈ 86 400 с ≈ 10⁵ с, поэтому 1M запросов в день ≈ 12 rps. Доступ к памяти ~100 нс, случайное чтение с SSD ~100 мкс, round trip внутри дата-центра ~0.5 мс, между континентами ~100–150 мс.

## Строительные блоки масштабирования
- **Вертикальное** масштабирование (машина побольше) простое, но ограниченное; **горизонтальное** (больше машин) требует сервисов без состояния.
- **Stateless-сервисы** за балансировщиком: любой экземпляр обслуживает любой запрос. Сессии уезжают в Redis или в токены (JWT).
- **Балансировщики**: L4 (TCP, по IP/порту) или L7 (HTTP: маршрутизация по пути или заголовку, терминация TLS). Алгоритмы: round robin, least connections, консистентное хеширование (липкость по ключу).
- Уровни **кэширования**: браузер, CDN, reverse proxy, кэш приложения (Redis), буферный кэш базы.
- Паттерны кэша: **cache-aside** (приложение читает кэш, при промахе читает БД и заполняет кэш), read-through, write-through, write-behind. Инвалидация по TTL плюс явное вытеснение при записи.
- **Cache stampede** (много промахов одновременно на горячем ключе): объединение запросов/блокировка, TTL с jitter, stale-while-revalidate.
- Базы: реплики для чтения, партиционирование, шардирование; денормализация; **CQRS** (отдельные модели для чтения).
- **Очереди** развязывают сервисы, сглаживают всплески, позволяют повторы и асинхронную работу.

## Паттерны надёжности
- **Таймауты** на каждый удалённый вызов. Вызов без таймаута может держать поток вечно.
- **Повторы** с экспоненциальной задержкой + **jitter**, с ограниченным числом попыток и только для идемпотентных операций.
- **Circuit breaker** (closed → open → half-open): перестать вызывать падающую зависимость и быстро отказывать (Resilience4j).
- **Bulkhead**: отдельные пулы потоков или лимиты соединений на каждую зависимость, чтобы одна медленная зависимость не исчерпала всё.
- **Rate limiting**, **load shedding**, **graceful degradation** (отдавать закэшированные или частичные результаты).
- **Ключи идемпотентности** для небезопасных операций (платежи): хранить ключ вместе с результатом и возвращать тот же результат при повторе.
- Резервирование по зонам доступности, health check-и и автоматический failover, бэкапы с *проверенным* восстановлением.
- **SLI** (что измеряешь), **SLO** (внутренняя цель, например 99.9% запросов быстрее 300 мс), **SLA** (договор со штрафами), error budget.

## Rate limiting
- **Token bucket**: токены пополняются с фиксированной скоростью до ёмкости; каждый запрос забирает один. Допускает всплески, держит среднюю скорость.
- **Leaky bucket**: запросы вытекают с постоянной скоростью; сглаживает трафик.
- Счётчик **fixed window**: просто, но около границ окон пропускает 2× лимит. **Sliding window** (лог или счётчик) это исправляет.
- Распределённые лимиты: счётчики в Redis, обновляемые атомарно (Lua-скрипт или `INCR` + `EXPIRE`).
- Отвечай `429 Too Many Requests` с заголовком `Retry-After`. Ограничивай по API-ключу, пользователю или IP.

## Согласованность данных в распределённых системах
- Компромиссы CAP/PACELC; eventual consistency приемлема для многих путей чтения (ленты, счётчики), но не для денег.
- Межсервисные процессы: саги, transactional outbox, идемпотентные консьюмеры.
- **Распределённые блокировки** (Redis, ZooKeeper, строка в БД) могут истечь, пока владелец на паузе (GC, сеть), поэтому защищай ресурс **fencing-токенами**. Выбор лидера через etcd/ZooKeeper/leases Kubernetes.
- Уникальные ID без координации: UUIDv7, Snowflake.

## Дизайн API
- REST: ресурсы как существительные, правильные методы и коды ответов. **Идемпотентные** методы: GET, PUT, DELETE (и HEAD, OPTIONS); POST и PATCH нет.
- Пагинация **курсорами** для больших или меняющихся коллекций; версионирование (`/v1/` или заголовки); единый формат ошибок (`application/problem+json`).
- **gRPC** для внутренних вызовов с низкой задержкой и строгими контрактами (HTTP/2, Protobuf, стриминг); **GraphQL**, когда клиентам нужны гибкие запросы.
- Push клиентам: polling, long polling, **SSE** (сервер → клиент), **WebSocket** (в обе стороны). Webhooks для уведомлений между серверами (подписывай и повторяй их).

## Классические задачи
- **Сокращатель ссылок**: base62 от уникального id (7 символов = 62⁷ ≈ 3.5 триллиона), много чтения, поэтому агрессивно кэшировать; 302, если нужна аналитика кликов, 301 позволяет браузерам кэшировать редирект.
- **Новостная лента**: fan-out on write (заранее посчитанные ленты, быстрое чтение) vs fan-out on read (дешёвая запись); гибрид для знаменитостей с миллионами подписчиков.
- **Чат**: WebSocket-шлюзы, порядок в пределах беседы, подтверждения доставки, присутствие, push-уведомления офлайн.
- **Платёжная система**: идемпотентность, бухгалтерский журнал с двойной записью, конечный автомат на каждый платёж, сверка с провайдером, никаких потерянных или двойных списаний.
- Ещё часто встречаются: rate limiter, сервис уведомлений, распределённый кэш, файловое хранилище (object storage + БД метаданных + CDN), планировщик задач, автодополнение поиска (trie или префиксный индекс), top-K (count-min sketch + куча).

## Observability
- **Логи** (структурированный JSON с correlation/trace id), **метрики** (RED: Rate, Errors, Duration для сервисов; USE: Utilization, Saturation, Errors для ресурсов), **трейсы** (OpenTelemetry, распределённые span-ы).
- Алерты на симптомы, которые чувствуют пользователи (burn rate SLO, доля ошибок, задержка), а не на каждую причину (CPU на 80%).
- Дашборды по сервисам; runbook на каждый алерт.
