# Kotlin и корутины

## Основы Kotlin для Java-разработчика
- **Null safety**: `String` vs `String?`; `?.` (безопасный вызов), `?:` (Elvis, значение по умолчанию), `!!` (бросает NPE), smart cast после проверок. Типы из Java это **платформенные типы** (`String!`): не проверяются, пока их не присвоят объявленному Kotlin-типу.
- `val` (только чтение) vs `var`; вывод типов; строковые шаблоны `"Hello, $name"`; `==` это `equals`, `===` сравнение ссылок.
- Классы и методы **final по умолчанию** (`open`, чтобы разрешить переопределение). Для прокси Spring используй плагин `kotlin-spring` (all-open); для JPA-сущностей `kotlin-jpa` (конструкторы без аргументов).
- `data class`: `equals`/`hashCode`/`toString`/`copy`/`componentN` из свойств первичного конструктора. Не для JPA-сущностей.
- `object` (синглтон), `companion object` (аналог static-членов; `@JvmStatic` для вызова из Java), `sealed` классы/интерфейсы с исчерпывающим `when`.
- **Функции-расширения**: разрешаются статически по объявленному типу; доступа к private-членам нет.
- Scope-функции: `let` (`it`, возвращает результат лямбды), `run`, `with`, `apply` (`this`, возвращает получателя: настройка объекта), `also` (`it`, возвращает получателя: побочные эффекты).
- Аргументы по умолчанию и именованные аргументы (`@JvmOverloads` для Java); checked исключений нет (`@Throws` для совместимости с Java).
- `List` это **интерфейс только для чтения**, а не неизменяемый список; `MutableList` добавляет изменение. `Sequence` ленивая, как стрим в Java.
- `inline`-функции копируют лямбду в место вызова: нет аллокации, есть нелокальный `return` и `reified` параметры типов.
- `lateinit var` (не-null, присваивается позже; чтение до этого → `UninitializedPropertyAccessException`); `by lazy { }` (вычисляется один раз, по умолчанию синхронизировано).

## Основы корутин
- `suspend fun` может приостановиться, не блокируя свой поток. Компилятор превращает её в **конечный автомат** с дополнительным параметром `Continuation` (continuation-passing style).
- Билдеры: `launch` (возвращает `Job`, без результата), `async` (возвращает `Deferred<T>`, результат через `await()`), `runBlocking` (блокирует текущий поток: только для `main` и тестов), `coroutineScope`, `withContext`.
- Корутины дешёвые: 100 000 штук укладываются в несколько МБ кучи.
- `delay()` приостанавливает; `Thread.sleep()` блокирует поток и всё, что на нём запланировано.

## Диспетчеры
- `Dispatchers.Default`: CPU-работа, потоков столько, сколько ядер.
- `Dispatchers.IO`: блокирующий I/O (JDBC, файлы), эластичный (64 потока или больше), делит потоки с Default.
- `Dispatchers.Main` (UI) и `Unconfined` (нужен редко).
- `withContext(Dispatchers.IO) { jdbcCall() }` переносит только этот блок на другой диспетчер и возвращается обратно.
- Блокирующие вызовы на `Default` голодят все корутины, которые его делят.

## Структурированная конкурентность
- Каждая корутина работает в `CoroutineScope`. Родитель завершается, только когда завершились его дети; отмена родителя отменяет детей.
- Упавший ребёнок **отменяет родителя и всех соседей** (в `coroutineScope` / обычном `Job`). `supervisorScope` / `SupervisorJob`: дети падают независимо.
- Избегай `GlobalScope`: его корутины не привязаны ни к какому жизненному циклу, поэтому утекают, а их ошибки теряются.

## Отмена и исключения
- Отмена **кооперативная**: точки приостановки (`delay`, `yield`, `withContext`, операции каналов) её проверяют; CPU-циклы должны вызывать `ensureActive()` или проверять `isActive`.
- `CancellationException` это нормальный сигнал; никогда его не глотай. `catch (e: Exception)` вокруг suspend-вызовов тоже его ловит: пробрасывай дальше.
- `withTimeout(ms)` бросает `TimeoutCancellationException`; `withTimeoutOrNull` возвращает null.
- `launch` передаёт исключения родителю (и в итоге в `CoroutineExceptionHandler`); `async` держит их до `await()`, но родительский scope всё равно роняет.
- `finally` выполняется при отмене; для suspend-очистки нужен `withContext(NonCancellable) { ... }`.

## Flow
- `Flow` это **холодный** асинхронный поток: блок `flow { emit(x) }` выполняется заново при каждом `collect`.
- Операторы: `map`, `filter`, `transform`, `flatMapMerge`, `debounce`, `catch`, `onCompletion`. `flowOn(Dispatchers.IO)` меняет контекст **верхней** (upstream) части.
- Backpressure естественный: `emit` приостанавливается, пока коллектор не готов. `buffer()` и `conflate()` это меняют.
- Горячие потоки: `StateFlow` (всегда есть текущее значение, conflated, отдаёт только отличающиеся значения: состояние), `SharedFlow` (настраиваемые replay и буфер: события).
- `Channel`: горячая очередь между корутинами; `Flow` обычно лучший API.

## Корутины vs потоки vs virtual threads
- Корутины: возможность библиотеки + компилятора с явным `suspend` ("раскраска" функций), встроенная структурированная конкурентность, работают на любой версии JVM и на Android.
- Virtual threads (Java 21): возможность JVM; существующий блокирующий код дешевеет без изменений, но структурированной конкурентности пока нет (API в preview).
- Не держи монитор через точку приостановки (приостановка внутри `synchronized` это ошибка компиляции); используй `Mutex.withLock { }` из kotlinx.coroutines.
- Spring: `suspend`-методы контроллеров (WebFlux и MVC), корутинные репозитории, возврат `Flow`, `@Transactional` на suspend-функциях с реактивным менеджером транзакций.
