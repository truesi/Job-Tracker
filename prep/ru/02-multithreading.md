# Многопоточность и Java Memory Model

## Потоки
- Способы запустить код параллельно: наследовать `Thread`, передать `Runnable`, отправить `Runnable`/`Callable` в `ExecutorService` или использовать virtual threads (`Thread.ofVirtual().start(...)`, `Executors.newVirtualThreadPerTaskExecutor()`).
- `start()` создаёт новый поток, который вызывает `run()`. Прямой вызов `run()` просто выполняет его в текущем потоке. Повторный `start()` бросает `IllegalThreadStateException`.
- **Состояния**: `NEW` → `RUNNABLE` → `BLOCKED` (ждёт входа в `synchronized` блок) / `WAITING` (`wait()`, `join()`, `park()` без таймаута) / `TIMED_WAITING` (`sleep`, `wait`/`join` с таймаутом) → `TERMINATED`.
- **Daemon** потоки не держат JVM. Когда остаются только демоны, JVM завершается, и их `finally` блоки могут не выполниться.
- `join()` ждёт завершения потока. `sleep()` не отпускает захваченные мониторы; `wait()` отпускает монитор.

## Прерывание
- Прерывание кооперативное: `interrupt()` только выставляет флаг. Цикл на CPU, который не проверяет `Thread.currentThread().isInterrupted()`, продолжит работать.
- Блокирующие методы (`sleep`, `wait`, `join`, `BlockingQueue.take`...) бросают `InterruptedException` и **сбрасывают** флаг.
- Никогда не глотай его: пробрось дальше или восстанови флаг через `Thread.currentThread().interrupt()`.

## synchronized
- У каждого объекта есть intrinsic lock (монитор). `synchronized` метод экземпляра блокирует `this`; `static synchronized` метод блокирует объект `Class`, поэтому они не мешают друг другу.
- Reentrant: поток, держащий лок, может войти в другой `synchronized` код на том же локе.
- Даёт **взаимное исключение и видимость**: всё, что записано до unlock, видно следующему потоку, который захватит тот же монитор.
- `wait`/`notify`/`notifyAll` требуют владения монитором (иначе `IllegalMonitorStateException`). Всегда вызывай `wait()` в цикле `while (!condition)`: бывают ложные пробуждения, и условие может измениться до повторного захвата лока.

## volatile
- Гарантирует **видимость и упорядочивание**: запись видна последующим чтениям, а компилятор и CPU не переставляют операции вокруг неё.
- **Не** даёт атомарности: `volatileCount++` это read-modify-write, и гонка остаётся. Используй `AtomicInteger`/`LongAdder` или лок.
- Типичные применения: флаги остановки, публикация неизменяемого объекта, поле в double-checked locking.
- Без `volatile` цикл `while (running) {}` может так и не увидеть `running = false`: JIT вправе вынести чтение из цикла.

## Java Memory Model: happens-before
- Порядок программы внутри одного потока.
- Unlock монитора → каждый последующий lock того же монитора.
- Запись в volatile → каждое последующее чтение той же переменной.
- `Thread.start()` → действия запущенного потока; действия потока → возврат из его `join()` в другом потоке.
- Final поля: значения, выставленные в конструкторе, видны всем потокам, если `this` не утёк во время конструирования.
- Нет ребра happens-before = **data race**: устаревшие значения, переупорядоченные записи, частично сконструированные объекты. `Thread.sleep` не создаёт ребра.
- Запись в не-volatile `long`/`double` может разбиться на две 32-битные (JLS 17.7).
- **Double-checked locking** требует `volatile` поля, иначе другой поток может увидеть ненулевую ссылку на недостроенный объект. Holder-класс или `enum` синглтон обходят проблему.

## Проблемы конкурентности
- **Race condition**: результат зависит от порядка выполнения (check-then-act, read-modify-write).
- **Deadlock** требует всех четырёх условий Коффмана: взаимное исключение, удержание и ожидание, отсутствие вытеснения, циклическое ожидание. Лечение: глобальный порядок захвата локов, `tryLock` с таймаутом, меньше вложенных локов. Находится через `jstack` или thread dump.
- **Livelock**: потоки постоянно реагируют друг на друга и не продвигаются. **Starvation**: поток никогда не получает CPU или лок (нечестные локи, приоритеты).
- Как избежать общего состояния: thread confinement, неизменяемые объекты, `ThreadLocal`. В пулах потоков всегда делай `ThreadLocal.remove()` в `finally`, иначе значения утекают в следующую задачу.

## Virtual threads (Java 21)
- Дешёвые потоки, которые JVM планирует на небольшое число carrier-потоков (`ForkJoinPool`). На блокирующем I/O virtual thread отмонтируется и освобождает carrier.
- **Pinning**: в JDK 21 virtual thread, заблокированный внутри `synchronized` или в native вызове, остаётся смонтированным на carrier. В JDK 24 (JEP 491) pinning для `synchronized` убрали.
- Не пуль virtual threads: создавай по одному на задачу. Доступ к дефицитным ресурсам (соединения с БД) ограничивай через `Semaphore`.
- Лучше всего подходят для I/O-bound кода в стиле thread-per-request. CPU-bound работу они не ускоряют.
