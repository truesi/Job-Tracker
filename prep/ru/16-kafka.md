# Kafka и обмен сообщениями

## Базовая модель
- **Топик** делится на **партиции**: упорядоченные логи, в которые только дописывают. У каждой записи есть ключ, значение, заголовки, timestamp и **offset** (позиция в партиции).
- **Порядок гарантирован только внутри партиции.** Партиционер по умолчанию отправляет записи с одинаковым ключом в одну партицию (`hash(key) % partitions`).
- Брокеры образуют кластер; у каждой партиции есть **лидер** и followers (replication factor). **ISR** = in-sync replicas, которые догнали лидера.
- Метаданными кластера управляет **KRaft** (собственный Raft-кворум Kafka); Kafka 4.0 убрала ZooKeeper.
- Записи **не удаляются при чтении**: хранение ограничено временем или размером. **Log compaction** вместо этого оставляет последнюю запись по каждому ключу; значение `null` (tombstone) удаляет ключ.

## Продюсеры
- `acks=0` (отправил и забыл), `acks=1` (лидер записал), `acks=all` (все in-sync реплики). При `replication.factor=3` и `min.insync.replicas=2` `acks=all` переживает потерю брокера без потери данных.
- **Идемпотентный продюсер** (`enable.idempotence=true`, по умолчанию с Kafka 3.0): повторы не создают дубликатов и не меняют порядок внутри партиции, пока жив продюсер.
- Пропускная способность: `linger.ms` (немного подождать, чтобы наполнить пакет), `batch.size`, `compression.type` (lz4, zstd). `send()` асинхронный; проверяй результат через callback или future.
- **Транзакции** (`transactional.id`): атомарная запись в несколько партиций плюс offset-ы консьюмера → exactly-once read-process-write внутри Kafka.

## Консьюмеры и группы консьюмеров
- Внутри **группы консьюмеров** каждая партиция назначена ровно одному консьюмеру. Параллелизм ограничен числом партиций: лишние консьюмеры простаивают.
- Разные группы получают **все** записи каждая (publish-subscribe).
- Offset-ы коммитятся во внутренний топик `__consumer_offsets`. Автокоммит (`enable.auto.commit`, по умолчанию каждые 5 с) против ручного коммита после обработки.
- Коммит **после** обработки → at-least-once (дубликаты после падения). Коммит **до** → at-most-once (потери после падения).
- **Ребалансировка** при входе, выходе или таймауте консьюмеров. Если между poll проходит больше `max.poll.interval.ms`, консьюмера выкидывают из группы. Cooperative sticky assignor и static membership (`group.instance.id`) уменьшают боль от ребалансировок.
- `auto.offset.reset` (`earliest`/`latest`) применяется только когда у группы нет закоммиченного offset.
- **Consumer lag** = последний offset лога - закоммиченный offset: главная метрика здоровья.

## Семантика доставки
- **At-most-once**, **at-least-once** (практический вариант по умолчанию), **exactly-once**.
- Exactly-once работает для обработки Kafka → Kafka (транзакции + `isolation.level=read_committed`). С внешними системами (база, HTTP API) получается at-least-once плюс **идемпотентные консьюмеры**.
- Идемпотентные консьюмеры: дедупликация по id события (таблица обработанных событий с уникальным ключом), upsert, естественные уникальные ограничения или бизнес-состояние, в котором операция становится пустой.

## Обработка ошибок
- Временные ошибки: повтор с задержкой. Постоянные ошибки (невалидные данные): после N попыток отправить в **dead letter topic** (DLT) и поднять алерт.
- **Блокирующие повторы** (повтор на месте) сохраняют порядок в партиции, но стопорят её; **неблокирующие повторы** (retry-топики) не стопорят партицию, но ломают порядок.
- **Poison pill**: запись, которую даже нельзя десериализовать, навсегда блокирует партицию. Оберни десериализатор (`ErrorHandlingDeserializer` в Spring Kafka).
- Spring Kafka: `DefaultErrorHandler` + `DeadLetterPublishingRecoverer` или `@RetryableTopic`.

## Решения при проектировании
- **Число партиций**: целевая пропускная способность / пропускная способность одной партиции, плюс достаточно для параллелизма консьюмеров. Его можно увеличить, но никогда нельзя уменьшить, а увеличение меняет соответствие ключ → партиция (ломая порядок по ключу на границе изменения).
- **Ключ**: id сущности, когда важен порядок по сущности (`orderId`). Избегай горячих ключей. Ключ `null` распределяет записи (sticky partitioner).
- **Схемы**: Avro/Protobuf/JSON Schema с Schema Registry; развивай их обратно совместимыми изменениями (добавляй необязательные поля, никогда не переиспользуй и не удаляй обязательные).
- **Kafka vs RabbitMQ**: Kafka это лог с повторным чтением и сроком хранения, offset-ы на стороне консьюмера, очень высокая пропускная способность и порядок по партиции. RabbitMQ это брокер, который доставляет и удаляет подтверждённые сообщения, с гибкой маршрутизацией (exchanges), TTL на сообщение и приоритетами.

## Spring Kafka
- `KafkaTemplate.send()` возвращает `CompletableFuture<SendResult>` (Spring Kafka 3.0+).
- `@KafkaListener(topics = "...", groupId = "...", concurrency = "3")`; batch-слушатели; фабрики контейнеров под разные конфигурации.
- Режимы подтверждения: `BATCH` (по умолчанию: коммит после обработки записей каждого poll), `RECORD`, `MANUAL`/`MANUAL_IMMEDIATE` с `Acknowledgment.acknowledge()`.
- Транзакции через `KafkaTransactionManager`. Транзакция БД и транзакция Kafka **не** атомарны вместе: для этого используй паттерн outbox.
