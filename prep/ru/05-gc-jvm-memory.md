# GC и память JVM

## Области памяти JVM
- **Heap**: все объекты. Молодое поколение (Eden + два Survivor) и старое поколение.
- **Metaspace**: метаданные классов в native-памяти. Заменил PermGen в Java 8 и не ограничен, пока не задан `-XX:MaxMetaspaceSize`.
- **Стеки потоков**: фреймы с локальными переменными и стеком операндов, по одному на поток (`-Xss`). Глубокая рекурсия → `StackOverflowError`.
- **Code cache**: код, скомпилированный JIT. **Direct buffers** (`ByteBuffer.allocateDirect`, Netty): вне кучи.
- Флаги: `-Xms`/`-Xmx` для кучи. В контейнерах `-XX:MaxRAMPercentage` (по умолчанию 25% от лимита контейнера).
- Виды OutOfMemoryError: `Java heap space`, `Metaspace`, `GC overhead limit exceeded`, `unable to create native thread`, `Direct buffer memory`.

## Основы сборки мусора
- Объект жив, если он достижим из **GC roots**: локальные переменные и параметры живых фреймов, static поля, JNI-ссылки, используемые мониторы. Недостижимые циклы тоже собираются: это трассировка, а не подсчёт ссылок.
- **Гипотеза поколений**: большинство объектов умирает молодыми. Minor (young) GC частый и дешёвый; объекты, пережившие несколько minor GC (возраст до 15), продвигаются в старое поколение.
- Алгоритмы: mark-sweep, mark-compact (без фрагментации), копирование (молодое поколение: живые объекты копируются из Eden + Survivor в другой Survivor).
- Паузы **stop-the-world** случаются в safepoint-ах. Card table и write barriers отслеживают ссылки старое → молодое, поэтому minor GC не сканирует всё старое поколение.
- Аллокация очень дешёвая: сдвиг указателя в собственном **TLAB** потока (thread-local allocation buffer).
- `System.gc()` это только подсказка.

## Сборщики
- **Serial**: один поток, для маленьких куч или контейнеров с 1 CPU.
- **Parallel**: многопоточный stop-the-world, лучшая пропускная способность. По умолчанию до Java 8.
- **G1** (по умолчанию с Java 9): куча разбита на одинаковые регионы (1–32 МБ), первыми собираются регионы с наибольшим количеством мусора, есть цель по паузе (`-XX:MaxGCPauseMillis`, по умолчанию 200 мс). Объекты размером ≥ половины региона *humongous*.
- **ZGC**: конкурентная разметка и перемещение, паузы меньше 1 мс независимо от размера кучи (до терабайт). Generational с JDK 21.
- **Shenandoah**: тоже конкурентное уплотнение (от Red Hat). **Epsilon**: только выделяет память и никогда не собирает, для тестов и бенчмарков.
- CMS объявили deprecated в 9 и удалили в 14.

## Ссылки
- **Strong**: обычные ссылки.
- **Soft**: очищаются только при нехватке памяти, гарантированно до OOM. Кэши, чувствительные к памяти (с осторожностью).
- **Weak**: очищаются на следующем GC, как только объект достижим только по слабым ссылкам. `WeakHashMap`, канонизирующие map.
- **Phantom**: `get()` всегда возвращает null; сигнализирует, что объекта больше нет, для очистки. На них построен `Cleaner`.
- `finalize()` объявлен deprecated for removal: непредсказуем, медленный и может воскрешать объекты. Используй try-with-resources и `Cleaner`.

## Утечки памяти в Java
- Утечка = объекты всё ещё достижимы, но больше не нужны. Типичные причины: static коллекции, которые только растут, кэши без вытеснения, неудалённые listener-ы, `ThreadLocal` в потоках пула, inner классы, держащие внешний экземпляр, утечки classloader-ов при редеплое.
- Симптом: заполненность старого поколения после каждого full GC продолжает расти.
- Инструменты: `-XX:+HeapDumpOnOutOfMemoryError`, `jcmd <pid> GC.heap_dump`, Eclipse MAT (dominator tree, retained size, path to GC roots), JFR + JDK Mission Control, логи GC (`-Xlog:gc*`), `jstat -gcutil`, async-profiler (профилирование аллокаций).

## JIT и загрузка классов
- Tiered compilation: интерпретатор → C1 (быстрая компиляция, профилирование) → C2 (агрессивная оптимизация) для горячих методов.
- Ключевые оптимизации: **inlining**, **escape analysis** (объект, который не утекает, можно разложить на скаляры и вообще не выделять в куче), разворачивание циклов, устранение локов. **Деоптимизация** происходит, когда допущение нарушается.
- Загрузчики классов: bootstrap → platform → application. **Parent delegation**: загрузчик сначала спрашивает родителя, поэтому никто не подменит `java.lang.String`.
- Жизненный цикл: загрузка → линковка (verify, prepare, resolve) → инициализация (static-инициализаторы, при первом активном использовании).
- `ClassNotFoundException`: не удалась явная загрузка по имени. `NoClassDefFoundError`: класс был при компиляции, но отсутствует (или не смог инициализироваться) в рантайме.
