# Индексы

## Что такое индекс
- Отдельная отсортированная структура, которая сопоставляет ключ → расположение строки (TID в PostgreSQL, первичный ключ во вторичных индексах InnoDB).
- Ускоряет чтение и замедляет запись: каждый `INSERT`, `DELETE` и многие `UPDATE` обязаны обновить **каждый** индекс, и каждый индекс занимает место на диске и в кэше.
- На них держатся ограничения: `PRIMARY KEY` и `UNIQUE` реализуются уникальными индексами. PostgreSQL **не** создаёт индексы на столбцах внешних ключей автоматически.

## B-tree
- Тип по умолчанию: сбалансированное дерево с большим fan-out (сотни ключей на страницу), обычно 3–4 уровня даже для сотен миллионов строк.
- Листья связаны и отсортированы, поэтому B-tree обслуживает `=`, `<`, `>`, `BETWEEN`, `IN`, `ORDER BY`, `MIN`/`MAX` и префиксный `LIKE 'abc%'` (в PostgreSQL с C collation или `text_pattern_ops`).
- Поиск O(log n): несколько чтений страниц, которые обычно уже в кэше.

## Составные индексы
- **Правило левого префикса**: индекс по `(a, b, c)` помогает запросам по `a`, `a, b` и `a, b, c`, но не по одному `b` (PostgreSQL 18 и MySQL 8.0.13+ в ограниченных случаях умеют skip scan).
- Порядок столбцов: **сначала столбцы с равенством, диапазон последним**. После условия-диапазона следующие столбцы уже не сужают поиск.
- Индекс может отдавать строки уже отсортированными: `(customer_id, created_at)` обслуживает `WHERE customer_id = ? ORDER BY created_at DESC LIMIT 10` без сортировки.
- Один составной индекс обычно лучше нескольких одностолбцовых для частого фильтра по нескольким столбцам.

## Покрывающие индексы и index-only scan
- Если индекс содержит все столбцы, нужные запросу, база может ответить только по индексу (**index-only scan**). PostgreSQL 11+: `CREATE INDEX ... (customer_id) INCLUDE (status, amount)`.
- PostgreSQL всё равно должен проверить видимость строк; index-only scan пропускает таблицу только для страниц, помеченных all-visible в visibility map (её поддерживает `VACUUM`).
- **InnoDB**: таблица *и есть* B-tree по первичному ключу (кластерный индекс). Вторичные индексы хранят первичный ключ, поэтому поиск по вторичному индексу проходит два дерева, а широкий первичный ключ раздувает все вторичные индексы.
- Случайные первичные ключи UUIDv4 разбрасывают вставки по кластерному индексу (расщепления страниц, плохое использование кэша). Лучше последовательные ключи: `BIGINT` identity или упорядоченные по времени UUIDv7.

## Другие типы индексов (PostgreSQL)
- **Hash**: только равенство.
- **GIN**: запросы "содержит" по массивам, `jsonb` (`@>`), полнотекстовый поиск, триграммный поиск (`pg_trgm`) для `LIKE '%abc%'`.
- **GiST**: геометрия, диапазоны, exclusion-ограничения (без пересекающихся бронирований), поиск ближайших соседей.
- **BRIN**: диапазоны блоков для огромных, естественно упорядоченных таблиц (логи только на добавление, по времени). Крошечный и дешёвый, но грубый.
- **Частичный**: `CREATE INDEX ... WHERE status = 'ACTIVE'`, индексирует только горячее подмножество.
- **По выражению**: `CREATE INDEX ... ON users (lower(email))`, подходит для `WHERE lower(email) = ?`.

## Когда индексы не используются
- Функция или арифметика над столбцом (`WHERE DATE(created_at) = ...`, `WHERE price * 2 > 100`).
- Неявное приведение типа (сравнение столбца `varchar` с числом в MySQL).
- Ведущий wildcard: `LIKE '%son'`.
- **Низкая селективность**: если подходит большая доля строк, последовательное сканирование дешевле множества случайных чтений страниц.
- Устаревшая статистика (запусти `ANALYZE`), маленькие таблицы, `OR` по разным столбцам (может стать BitmapOr или seq scan), `<>`/`NOT IN`.
- Планировщик PostgreSQL стоимостной: он оценивает число строк по статистике (число различных значений, самые частые значения, гистограммы) и выбирает самый дешёвый план.

## Как читать EXPLAIN
- Узлы сканирования: `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Index Scan` + `Bitmap Heap Scan` (много строк из индекса, чтение в порядке страниц).
- Узлы соединения: `Nested Loop`, `Hash Join`, `Merge Join`.
- `EXPLAIN (ANALYZE, BUFFERS)`: сравни оценку и фактическое число строк, найди самый медленный узел, посмотри на `Rows Removed by Filter` и на чтения с диска против попаданий в кэш.

## Обслуживание индексов
- Неиспользуемые индексы: `pg_stat_user_indexes.idx_scan = 0` (за достаточно долгий период и на всех репликах).
- Создание без блокировки записи: `CREATE INDEX CONCURRENTLY` (медленнее, нельзя в транзакции, при сбое оставляет INVALID индекс). Раздутые перестраивай через `REINDEX CONCURRENTLY`.
- **HOT updates** в PostgreSQL: если ни один индексированный столбец не меняется и на странице есть место, обновление вообще не трогает индексы. Ещё одна причина не индексировать всё подряд.
