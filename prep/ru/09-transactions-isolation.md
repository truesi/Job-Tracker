# Транзакции и изоляция

## ACID
- **Atomicity**: всё или ничего; сбой откатывает всё.
- **Consistency**: ограничения и инварианты выполняются до и после. В основном это забота приложения, с помощью ограничений БД.
- **Isolation**: конкурентные транзакции не видят промежуточное состояние друг друга, в меру уровня изоляции.
- **Durability**: закоммиченная транзакция переживает сбой. Write-ahead log (WAL) сбрасывается на диск (fsync) до того, как `COMMIT` вернёт управление.

## Аномалии чтения
- **Dirty read**: чтение данных, которые другая транзакция ещё не закоммитила (и может откатить).
- **Non-repeatable read**: два чтения одной строки дают разные значения, потому что между ними другая транзакция закоммитила изменение.
- **Phantom read**: повторный запрос по диапазону возвращает новые строки, вставленные другой транзакцией.
- **Lost update**: два цикла read-modify-write по одной строке; вторая запись затирает первую.
- **Write skew**: две транзакции читают пересекающиеся данные и обновляют *разные* строки, вместе нарушая инвариант (два врача одновременно снимают с себя дежурство, и не остаётся никого).

## Уровни изоляции
- Уровни стандарта SQL: `READ UNCOMMITTED` < `READ COMMITTED` < `REPEATABLE READ` < `SERIALIZABLE`, определяются тем, какие аномалии запрещены.
- **PostgreSQL**: по умолчанию `READ COMMITTED`. `READ UNCOMMITTED` ведёт себя как `READ COMMITTED`. `REPEATABLE READ` это snapshot isolation (фантомов тоже нет; конкурентное обновление той же строки даёт ошибку сериализации). `SERIALIZABLE` это SSI: дополнительно ловит write skew и откатывает одну из транзакций с SQLSTATE `40001`.
- **MySQL InnoDB**: по умолчанию `REPEATABLE READ`, со snapshot-чтением плюс next-key (gap) локами для блокирующих чтений.
- **Oracle**: по умолчанию `READ COMMITTED`; его `SERIALIZABLE` это snapshot isolation.
- Выше изоляция = больше откатов или блокировок. Код обязан **повторять** транзакции при ошибках сериализации.

## MVCC
- Multi-version concurrency control: писатель создаёт новую версию строки, читатели продолжают видеть версию из своего снимка. **Читатели не блокируют писателей, писатели не блокируют читателей.**
- `READ COMMITTED`: новый снимок на каждый оператор. `REPEATABLE READ`/`SERIALIZABLE`: один снимок на транзакцию.
- PostgreSQL хранит старые версии прямо в таблице (`xmin`/`xmax` у каждой строки); мёртвые убирает `VACUUM`. InnoDB и Oracle хранят старые версии в undo log.
- Долгие сессии или сессии "idle in transaction" мешают очистке: раздувание, медленные запросы, а в пределе wraparound идентификаторов транзакций.

## Блокировки
- Блокировки строк: `SELECT ... FOR UPDATE` (эксклюзивная), `FOR SHARE`, `NOWAIT` (ошибка вместо ожидания), `SKIP LOCKED` (брать только свободные строки: очереди задач).
- Писатели блокируют изменяемые строки до коммита, поэтому два обновления одной строки выполняются по очереди.
- DDL берёт сильные блокировки таблицы (`ACCESS EXCLUSIVE` в PostgreSQL); ожидающий `ALTER TABLE` блокирует все запросы за собой. В миграциях выставляй `lock_timeout`.
- **Deadlock**: база находит цикл и откатывает одну транзакцию. Предотвращай единым порядком захвата блокировок; обрабатывай повтором.
- Advisory locks (`pg_advisory_xact_lock(key)`) блокируют ключи, определённые приложением.

## Оптимистичная и пессимистичная блокировка
- **Пессимистичная**: сначала заблокировать (`FOR UPDATE`), потом менять. Хороша при высокой конкуренции и коротких транзакциях.
- **Оптимистичная**: столбец `version`; `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`; 0 обновлённых строк означает конфликт: повторить или сообщить пользователю. В JPA это `@Version`. Хороша при низкой конкуренции и долгом "времени на подумать" у пользователя.
- Часто не нужна ни та, ни другая: атомарный оператор вроде `UPDATE accounts SET balance = balance - 100 WHERE id = ? AND balance >= 100`, затем проверка числа строк.

## Spring @Transactional
- Работает через **прокси**: вызовы изнутри того же класса (self-invocation) его обходят, как и метод, который прокси не может перехватить (private, final).
- Откатывает при `RuntimeException` и `Error`; **checked исключения коммитятся**, если не указать `rollbackFor`.
- Propagation: `REQUIRED` (по умолчанию: присоединиться или создать), `REQUIRES_NEW` (приостановить внешнюю транзакцию, выполнить отдельную на другом соединении), `NESTED` (savepoint), `SUPPORTS`, `MANDATORY`, `NOT_SUPPORTED`, `NEVER`.
- `readOnly = true`: Hibernate пропускает dirty checking и flush; соединение помечается read-only (становится возможна маршрутизация на реплику).
- "Transaction silently rolled back because it has been marked as rollback-only": внутренний метод с `REQUIRED` бросил исключение, а внешний его поймал и попытался закоммитить.
- Держи транзакции короткими: никаких HTTP-вызовов и ожидания пользователя внутри, потому что они держат соединение и блокировки.

## Распределённые транзакции
- **2PC / XA**: координатор проводит prepare, затем commit по всем ресурсам. Блокирующий протокол (участники держат блокировки, ожидая координатора) и редкость в микросервисах.
- **Saga**: последовательность локальных транзакций с компенсирующими действиями при сбое, через оркестрацию (центральный координатор) или хореографию (события).
- **Transactional outbox**: бизнес-изменение и событие пишутся в одной транзакции БД; relay (polling или CDC через Debezium) публикует событие. Потребители должны быть **идемпотентными** (доставка at-least-once).
